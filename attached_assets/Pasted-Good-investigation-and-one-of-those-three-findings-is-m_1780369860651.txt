**The two `006_` files is the finding I want you to slow down on, because renumbering a migration is not as safe as it sounds.** You have `006_add_batch_number_to_orders.sql` AND `006_add_order_items.sql`, a numbering collision. The instinct is "renumber one to 008." Here's the trap: **the migration runner tracks applied migrations by filename in `schema_migrations`.** If `006_add_order_items.sql` has already run and been recorded under that filename on dev (and possibly prod), and you rename it to `008_add_order_items.sql`, the runner now sees `008_...` as a *new, unapplied* migration and tries to run it again, while the old `006_...` record points at a file that no longer exists. Depending on how the runner behaves, you either get a re-run (hopefully idempotent, so harmless) or a tracking-state mismatch that's exactly the journal-divergence mess you spent hours untangling earlier this session.

So renumbering a migration that's *already been applied somewhere* is risky. Before the plan renames anything, answer: **have both 006 files already run and been recorded in `schema_migrations` on dev and prod?**

- If **neither has been applied anywhere** (purely local, uncommitted, never run) → renaming is safe, just rename one to the next free number.
- If **either has already run and is recorded** → renaming changes its tracking identity and the runner may re-run or lose track of it. In that case the safer move is *not* to rename the file but to reconcile carefully: keep the filenames as-is if the runner can tolerate the collision, or rename AND update the `schema_migrations` record to match, in one coordinated step, so tracking stays consistent.
