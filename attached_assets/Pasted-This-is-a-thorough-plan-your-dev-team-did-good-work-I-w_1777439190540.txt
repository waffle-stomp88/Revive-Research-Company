## Things to clarify or push back on ⚠️

**1. The Site URL setting (#5 in the manual checklist) needs more care.**

They wrote: *"configure 'Site URL' to https://reviveresearch.co (production) or the Replit dev URL"*

This is ambiguous. Supabase's Site URL is what gets used in password reset emails and OAuth redirects. **You need both** — production Site URL set to `https://reviveresearch.co`, AND the Replit dev URL added to the **Additional Redirect URLs** allowlist in Supabase. Otherwise, password reset emails sent during dev testing will redirect users to production (broken), or production password resets will fail because the dev URL is set as primary.

**Ask them to clarify:** "Set Site URL to production (`https://reviveresearch.co`) and add the Replit dev preview URL to the Additional Redirect URLs allowlist. Both need to work."

**2. Email sender — they didn't address this at all.**

By default, Supabase password reset emails come from `noreply@mail.app.supabase.io`. For 7 users this is okay, but it looks unprofessional and may hit spam filters since it's a generic domain. Two options:

- **Quick:** Live with the default Supabase sender for the cutover (7 users, you're warning them via personal email anyway)
- **Better long-term:** Configure Supabase Auth to use Amazon SES (which you already use) so reset emails come from `noreply@reviveresearch.co`. This is in **Supabase dashboard → Authentication → Emails → SMTP Settings**.

I'd do the cutover with default Supabase sender, then set up SES integration as a follow-up task. **Don't let SES setup block the migration.** But ask your dev team to add it to the post-migration cleanup list.

**3. The migration is irreversible per user — make sure you understand this.**

Their rollback plan correctly notes: *"User IDs that have been migrated (new Supabase UUIDs) remain in the DB — the lazy migration is one-directional and permanent per user"*

This means: once a user logs in via Supabase, their ID is permanently changed in your database. If you roll back to Auth0 after that user has logged in, **that user's Auth0 ID won't match anything in your DB anymore.** They'd appear as a new user.

For 7 pre-launch users this is acceptable risk, but **the implication is: you shouldn't tell your 7 users to log in via Supabase until you're 100% confident the migration is staying.** Don't have them log in just to "test it out." First successful login = permanent commitment for that user.

**4. The `isAdmin` field migration — make sure it's preserved.**

The migration SQL preserves `is_admin` in the new row insert (line: `SELECT $new_id, email, first_name, last_name, profile_image_url, is_admin, created_at, NOW()`). Good. But **confirm with your dev team:** is the `is_admin` flag set on any of the 7 users currently? If you're an admin user yourself in the existing system, you don't want to log in post-migration and find yourself locked out of admin panels because the flag didn't carry over. **Verify before cutover.**

**5. Email confirmation for new email/password signups — is it on or off?**

Supabase has a setting under **Authentication → Email** called "Confirm email." If it's on (default), users who sign up with email/password get a confirmation email and can't log in until they click it. If it's off, they're logged in immediately.

**For the existing 7 users:** they're not signing up — they're using the password reset flow, so this doesn't apply.
**For new users post-launch:** you almost certainly want email confirmation ON for an e-commerce site, to prevent fake accounts. But this means the lazy migration only triggers AFTER email confirmation, which adds a step.

**Ask your dev team:** "Is email confirmation enabled? If yes, document this in the user-facing flow so we know what to expect."

**6. The "users.id" foreign key change — does Drizzle's schema need updating?**

Currently `users.id` is a varchar (storing `auth0|xxx`). Supabase UUIDs are also valid varchar/text, so the column type doesn't NEED to change. But it's worth asking: **should the Drizzle schema definition for `users.id` be explicitly typed as UUID going forward?** Or kept as varchar to handle both legacy and new IDs gracefully during the transition window?

I'd vote: **keep as varchar.** UUID typing would break for any user who hasn't logged in yet (still has `auth0|xxx` ID). After all 7 users have migrated and you've confirmed no legacy IDs remain, you can tighten the type if you want.

**7. Test the migration on a DB copy first — your dev team didn't include this.**

Their plan jumps from "write the code" straight to "deploy and verify." For a migration that **permanently rewrites primary keys across 13 tables**, you want a dry run.

**Add to the plan:** Before running the migration code on production, clone the production database to a staging environment, run the full migration flow with a test user account, and verify all 13 tables update correctly and no data is orphaned. This adds maybe a day of work but eliminates the worst-case scenario.
