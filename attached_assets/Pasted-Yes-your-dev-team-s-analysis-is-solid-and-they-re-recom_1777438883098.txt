## Things I want to make sure they include in the task

**1. The "match by email" approach has one gotcha — handle it explicitly.**

What happens when an existing user logs in for the first time post-migration? The flow needs to be:

1. User logs in via Supabase (gets a new Supabase UUID)
2. Backend's `/api/auth/sync` receives the Supabase user info
3. Backend checks: does a user with this email already exist in our DB with an `auth0|` prefixed ID?
4. **If yes:** Run the ID swap — update that user's ID to the new Supabase UUID, and cascade-update every foreign key reference (orders, affiliate accounts, research profiles, etc.)
5. **If no:** Normal new user flow

This is the critical logic. Make sure your dev team writes this as a **one-time migration on first login** per existing user, not a script run upfront. Reason: you can't generate the Supabase UUIDs ahead of time for the email/password users — those get created when the user actually signs up via Supabase.

**Alternative (cleaner):** Pre-create the 7 Supabase user accounts via the Supabase admin API, get their UUIDs immediately, and run a one-shot migration script to update all the foreign keys before launch. Then send password reset emails. This way the migration is done and dusted, not happening lazily on each user's first login.
